Deep Interview Pattern

Use this reference when a request needs clarification before planning or execution.

Unknowns Pass

  • Read obvious local context before asking: AGENTS, README, task cards, design docs, source files.
  • Run a map-vs-territory check: prompt claims, repo proof, absent user context, and unasked constraints.
  • Use the taxonomy: known known, known unknown, unknown known, unknown unknown.
  • Classify gaps as discoverable facts, human preferences, or dangerous assumptions.
  • Emit unknown cards with type, why it matters, resolve-by route, and next probe.
  • Pick the highest-risk cheap probe before asking the user when possible.
  • Produce a better next prompt or refined brief that carries the unknowns forward.
  • Ask for a prompt-safe summary first when the supplied context is too large.

Example

Vague request: "make the project dashboard more useful before coding."

Unknowns Pass
- Map vs territory: "more useful" sounds like UX scope, but the repo may already encode task schemas, views, and writeback constraints.
- Known knowns: target surface is the project dashboard; implementation should not start yet.
- Known unknowns: which workflow is painful, which users/views matter, which data is authoritative.
- Unknown knowns: the user may have a private mental model of daily review vs project review that is not in repo docs.
- Unknown unknowns: changing completion flow may corrupt source-of-truth task state if schema/writeback rules are missed.

| Unknown | Type | Why it matters | Discoverable or user-required | Next probe | Risk if wrong |
|---|---|---|---|---|---|
| Source-of-truth rules | Known unknown | UI changes may write invalid status | Discoverable | Inspect task-state contract and dashboard schema | Data drift |
| "Useful" workflow | Unknown known | Design target depends on user's routine | User-required | Ask one workflow-ranking question | Pretty but unused UI |
| Completion semantics | Unknown unknown | Done flow may mix planned and actual time | Discoverable | Inspect existing completion schema and work traces | Incorrect records |

Highest-risk probe: inspect schema/writeback contract before asking for UI taste.
Local probes: task-state contract, dashboard schema, current route structure.
One user question: Which workflow should this optimize first: daily triage, project review, or completion writeback?
Better next prompt / refined brief: "Improve dashboard daily triage without changing writeback semantics unless confirmed..."
Carry-forward risk: visual preference remains open until after source-of-truth constraints are known.

Depth Profiles

  • Quick: low-risk ambiguity, usually no more than 5 rounds.
  • Standard: default requirements interview, usually no more than 12 rounds.
  • Deep: high-risk or branching work, usually no more than 20 rounds.

Question Style

  • Ask one question at a time.
  • Ask only questions that change scope, risk, design, or acceptance.
  • Prefer concrete options with tradeoffs over open-ended prompts.
  • Do not ask for facts that can be discovered from the repo or official docs.
  • Use concrete scenarios to expose decision boundaries and hidden assumptions.

Readiness Gates

  • Goal, scope, and acceptance criteria are executable.
  • Non-goals are explicit.
  • Decision boundaries are explicit.
  • Residual risk is named and acceptable for the next lane.
